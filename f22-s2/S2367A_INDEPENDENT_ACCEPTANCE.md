## 四項已用反例證明的**整合阻擋**（負向案例執行通過 ≠ 功能安全通過）
1. **會員口徑：** #459 `COUNT(DISTINCT CASE WHEN identity LIKE 'member:%' ...)`，只計已註冊會員；#466 只收所有 64 位元假名 `memberKey`，不區分訪客。故匿名訪客若被投影為假鍵，會被統計為會員（已本機重現）。需在可信來源規範 `verifiedMemberKey` 和訪客處理。
2. **時間篩選：** #459 `createdAt<now` 有完整時間界線；#466 `statsFake(today)` 按當天日期計算。對先前已匯入資料做歷史的日內時間查詢時，可能含指定時間之後的事件（已重現）。需 AI2 統一時間切片契約；若 UI 僅日曆整日，須明示。
3. **全帳號額度並發：** 同一筆 78,000 列寫入快照，兩批各 40 件×32 假預留，同時各自通過；合計預測 80,560 列，會跨過 80% 門檻（已重現）。#466 的 guard 是「假快照評估」而非全帳號原子預約；還缺多 Worker／跨 App 真權威和 Cloudflare 查用量。**不可宣稱已能保證免費或跨 App 防超限。**
4. **跨裝置事件身分：** 相同會員/音檔/時間的兩筆資料若各裝置給不同 eventKey，#466 會計兩次（已重現）。只有可信來源保證同一物理請求具有全域穩定 eventKey 才能保證防重。
