# Starry ID｜訪客權限獨立資料架構 v1

## 核心約束

「訪客」是 **權限主體**，不是會員資料；在管理員「全部會員」清單最上方固定呈現，但**不得**加入 `users`、`profiles`、`app_memberships`、`starry_app_access_decisions`，亦不得計入會員人數、獎銜查詢、會員多選/全選、會員資料與批次設定。管理員有權開關某個 App 的**明確公開功能**，不是替訪客偽造登入。

### 三張獨立表（與會員資料零關聯）

- `starry_guest_app_policies`：每個 App 獨立記錄 `allowed`（0/1），沒有紀錄預設禁止。更改人與時間供追溯。
- `starry_guest_app_previews`：管理員短效預覽（5 分鐘），送出前必須輸入「確認變更」。
- `starry_guest_app_operations`：誰在何時更動，保留舊值和新值及可預覽還原的 UUID。若別人已再次修改，舊操作不能覆蓋當前設定。

管理 API 全部通過原有 Starry ID **中央超級管理員驗證**，POST 限官方網站來源；不對訪客公開。開放訪客並不等同變更會員自身 App 權限。

## 已接入與未接入的判斷

來源：`worker/starryGuestAppAccess.ts` 的 `GUEST_ADAPTERS`。只有在 **該 App 的正式 Worker 已加入公開功能白名單並確認安全**後，才可加入此清單供管理員開關。

- `downloadstarry`：已完成匿名首頁互動的後端隔離。訪客可看首頁並操作非會員 UI；**不包括實際下載與會員紀錄**。資料表缺失、功能失效或無設定，都維持禁止。
- 其他 App：管理員頁面顯示「尚未接入」，按鈕不可操作；不得顯示假的已開放狀態。

## 建立下一個 App 訪客權限的流程

1. App 擬定「公開功能清單」及拒絕「會員專屬 API 清單」。
2. 在 App Worker 統一伺服器驗證，防止繞過前端遮罩。不得因 Guest allow 而把一般 App 會員授權誤當通過。
3. 決定匿名配額、Cloudflare 免費方案成本、速率限制，必要時禁止匿名高成本操作。
4. 測試匿名拒絕與允許、已登入禁止、會員個資隔離、被停權會員不得使用訪客旁路、中央資料庫故障時預設拒絕。
5. App PR 通過並完成正式部署後，才於 Starry ID `GUEST_ADAPTERS` 追加 App ID 與實際開放範圍；該 App 未列入中央清單時即使有殘留資料庫許可也忽略。
6. Starry ID PR 另行測試及部署；預設禁止，等待管理員確認後再開放。

## 使用者介面

管理員開啟 Starry ID 的「會員管理」：**訪客**位於真實會員清單第一項，沒有會員勾選框。點擊切換到獨立訪客設定頁，各 App 可見目前是否已接入、目前是否開放、實際適用功能。開放／禁止後都先預覽、輸入確認，完成人工操作留下可供預覽還原的 UUID。歷史還原亦再預覽，防止誤操作。

## 測試及回滾

需要測試：會員數不變、批次勾選不受訪客污染、預設拒絕、未整合強制禁止、只有管理員可操作、重複確認不會套用兩次、審計與可回復、已開放不越權私人 API、跨 App 中央身分同步。

回復應先撤銷 Guest allow，再針對本次 Cloudflare Worker 版本執行回退；資料表保持獨立，不刪除既有審計記錄與任何會員紀錄。
